## Landing and work doctrine

Exactly one proposed default landing per role below. An authorized intended destination following login takes precedence; do not interrupt a citizen returning to a draft. Multi-role default needs an explicit account preference or Chief Architect ordering, not whichever permission happens to be evaluated first. No new dashboards or permissions are implied.

Inbox = what do I need to do? Applications = find/inspect a case. Application = authoritative case record and currently available actions. Role access is necessary but not sufficient reason for permanent navigation. Dashboard remains an optional overview, not another queue. Settings and logout remain account-menu items.

`EVAL` = `/staff/permit-applications/{permitApplication}/evaluation`; `ASSESS` = `/staff/assessments/{assessment}`; `PAY` = `/staff/payment-schedules/{paymentSchedule}`; `CERT` = `/staff/post-payment-certifications/{certification}`; `PERMIT` = `/staff/permit-applications/{permitApplication}/uat-permit`. These names describe existing destinations, not new routes.

## Source proof and limits

`app/Actions/BuildMunicipalWorkInbox.php` is the common task source: active institutional assignments select office/capability tasks; completed authoritative records suppress pending tasks. `item()` preserves the corrected ordinary UAT permit destination while retaining the separate classic-cleanroom branch. `AssessmentCounterCheckReadiness` is shared by Inbox and Assessment presentation. Do not reintroduce a second presentation-derived readiness rule.

`resources/js/pages/work-inbox/Index.vue` provides search, task/year filters, count, named task, office, application identity, pagination and empty state: “No applications require action for this position.” It separately shows “No active municipal position.” Empty is not proof that all municipal work is complete: role assignment, filters and authorization affect the result.

The existing normal authentication fallback is `/dashboard` (`config/fortify.php`); the proposed per-role landings are not implemented. Sidebar already contains Inbox for staff. Dashboard does not. Certification and Mayoral pages return to Application rather than an explicit Inbox link, though the global sidebar remains accessible. Their generic task button “Open Application” can lead to Assessment, payment or certification: recommend naming the destination/action without changing `action_url` semantics.

Inbox-first is feasible for the certified municipal lifecycle based on source coverage. This audit does **not** re-run completed Application 291 or create pending work to demonstrate each state. Gate 10G must independently verify arrival, authorized action, completion, queue disappearance and return for each role using separately authorized acceptance evidence. A missing task or conflicting readiness is a genuine blocker, not permission to bypass the ceremony.

Citizen, historical and report roles do not need fake Inbox tasks. A current staff-wide Business Directory is not established by the workflow baseline; do not label a historical directory as the current business registry merely to fill the proposed menu.
