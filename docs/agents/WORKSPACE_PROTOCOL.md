# Multi-Agent Workspace Protocol

Status: **Required operating protocol**

## One Integrator, Separate Worktrees

The Chief Architect and Integrator is the only agent that integrates to `main`, resolves cross-agent conflicts, updates program-wide claims, or declares a milestone complete.

Each specialist receives a separate worktree and branch from one clean base commit. Suggested branch names:

```text
agent/migration/<packet-name>
agent/ui/<packet-name>
```

Never run two agents in the same worktree. Never begin from uncommitted changes owned by another agent.

## Assignment Contract

Every packet must state:

- objective and non-goals;
- exact base commit;
- owned files or globs;
- files reserved to the integrator or another agent;
- canonical evidence to read;
- acceptance criteria;
- required tests and browser checks;
- whether private artifacts are required;
- Board Trigger conditions.

If any of these are missing, stop before editing and ask the Chief Architect for the bounded packet.

## Shared Files Reserved To The Integrator

Unless explicitly delegated, specialists do not edit:

- `.ai/rules/**`;
- `docs/architecture/**`;
- `docs/reports/**`;
- `docs/implementation/PARITY_LEDGER.md`;
- `docs/implementation/MILESTONE_SCENARIOS.md`;
- `docs/agents/**`;
- root `AGENTS.md`;
- cross-cutting lifecycle scenario registries and shared browser-runner orchestration;
- shared authorization, assessment, receipt, permit-authority, or migration-executor contracts.

Specialists include proposed ledger, rule, and program-report updates in their handoff. The integrator applies them after review.

## Change Boundaries

### Migration Engineer

May change only migration/reconciliation code, focused tests, and directly assigned payload-safe implementation documentation. Must not alter current operational business semantics or frontend behavior.

### UI/UX Engineer

May change only assigned Vue/Inertia presentation, reusable UI components, styling, accessibility, and focused frontend/browser tests. Must not alter domain actions, financial calculation, migration, policy, authorization, or authority semantics.

### Chief Architect And Integrator

Owns cross-boundary changes, domain decisions, shared read models, final scenario composition, parity status, Board reports, integration verification, and release claims.

## Concurrency Rules

- Prefer disjoint file ownership.
- A specialist must not edit a file already assigned to another active packet.
- Generated files must be regenerated by the integrator if two packets would touch them.
- Database migrations, shared enums, route names, shared types, and scenario registries require integrator coordination before editing.
- Do not rebase or force-push another agent's branch.
- Do not cherry-pick unreviewed specialist commits directly to `main`.

## Required Engineering Process

1. Confirm branch, base commit, and clean worktree.
2. Read root `AGENTS.md`, matching `.ai/rules`, and role handoff.
3. Inspect sibling code and tests before editing.
4. Use Laravel Boost version-specific documentation before framework changes.
5. Implement the smallest coherent packet.
6. Run focused tests first.
7. Run Pint for PHP changes, focused PHPStan where established, frontend checks for UI changes, and browser verification where visible behavior changes.
8. Inspect generated artifacts and screenshots rather than relying only on exit codes.
9. Commit one coherent packet on the specialist branch.
10. Produce the handoff contract below.

## Handoff Contract

Every specialist returns:

```text
Role:
Packet:
Base commit:
Head commit:
Files changed:
Business capability affected:
What is proven:
What is not claimed:
Tests and formatters:
Browser verification:
Evidence artifact paths:
Production access or mutation:
External or irreversible actions:
Proposed parity/rule/doc updates:
Open risks or Board Triggers:
Repository status:
```

No claim is accepted without its verification state. `Implemented`, `tested`, `browser verified`, and `parity verified` remain distinct.

## Integration Gate

The Chief Architect reviews:

- architectural consistency;
- source and evidence traceability;
- authorization and authority semantics;
- financial and migration invariants;
- test quality and regression risk;
- browser artifacts for user-visible changes;
- sensitive-data exposure;
- compatibility with changes integrated since the specialist base.

The integrator may request corrections, cherry-pick, rebase in the integration worktree, or reimplement a narrow portion. Specialist success does not guarantee integration.

After integration, the Chief Architect runs the combined relevant suite and updates shared parity/evidence records.

## Board Triggers

Specialists stop their affected line and report immediately when proceeding would require:

- a material architecture change;
- invented business, fiscal, Treasury, numbering, identity, or authority policy;
- altered taxpayer liability;
- uncertain legal-identity merge;
- present permit issuance, release, validity, or legal-effect assertion;
- destruction or rewriting of source evidence;
- production mutation or irreversible migration;
- weakened operational, audit, rollback, or evidence boundary;
- contradiction with a Golden Financial Specimen or accepted Board decision.

Routine implementation uncertainty is not a Board Trigger. The Chief Architect determines escalation.

## Secret And Production Safety

- No credentials in source, prompts intended for broad circulation, commits, manifests, screenshots, or handoff documents.
- Private production artifacts remain in approved private storage.
- Production access is read-only unless a written authorization names the exact operation.
- Never use the unauthenticated legacy report endpoint for migration acquisition.
- Never use names, contact details, amounts, adjacency, or similarity as identity authority.
